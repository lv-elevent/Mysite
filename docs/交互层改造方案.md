# 交互层改造方案：滚动驱动 → 交互驱动

> 目标：把「滑滚轮更新内容」改成「点形象上的元素触发对应模块」。
> 本文只覆盖**交互层**；形象形式（3D 建模 / 2D 插画）押后决定，当前用现有 `me.glb` 当占位。

---

## 1. 为什么这个改动比看起来便宜

现有管线是单向的（`web/src/scene/Scene.tsx:328-406`）：

```
window.scrollY
  → 测量履历 DOM 锚点 [data-point="focus-N"] 的 rectTop   （第 349-365 行）
  → sTarget（连续索引，-1 … M-1）
  → frameTarget = (sTarget + 1) * FRAMES_PER_NODE          （第 370 行）
  → frameSmooth 缓动                                        （第 397 行）
  → mixer.setTime(frame / FPS)                              （第 401-406 行）
  → 同时驱动「相机运镜」+「角色动画」
```

再叠加视差、景深、眼球跟随。

**关键结论：滚动只是生产 `frame` 这个数值的一种输入方式。** `frameTarget` 之后的所有环节都不关心这个数值是谁给的。所以改造范围就是「`scrollY` → `sTarget`」那一段（第 331-366 行）+ 作品区映射（第 371-393 行），共约 60 行。

同时 `frameSmooth` 的缓动**天然就是「相机飞过去」的动画**，不用另写补间。

### 现成可复用的抓手

| 位置 | 现状 | 新用途 |
|---|---|---|
| `store.ts` | 已有 `active` / `hovered` / `entered` + `setActive` / `setHovered` / `enter`，一直没被真正用起来 | 直接作为交互状态层，把 `active` 收敛为模块 id |
| `me.glb` 的 `focus-1..5` | 5 个时间轴相机锚点 | 取前 4 个当 4 个模块的停靠点（`focus-0` 仍是总览） |
| `ui/Resume.tsx` | 履历时间轴 + `RESUME.en/zh` 数据 | 模块 2 的内容源 |
| `data/works.ts` + `ui/Works.tsx` | 作品集数据 + 横向画廊 | 模块 1 的作品集部分 |
| `ui/SocialIcons.tsx` | 社交图标 | 模块 4 的联系方式 |
| `utils/webgl.ts` | `hasWebGL2()` | 降级分支继续复用 |

**不用动 `blender/sen.blend`，不用重新烘焙 glb** —— 这是能在本轮就跑通交互的前提。

## 2. 目标架构：五层，交互层与渲染层解耦

```
┌─ 数据层   src/data/modules.ts          4 个模块：id / 名称 / 锚点 / 热点 / 内容来源
├─ 状态层   src/store.ts                 active / hovered / entered
├─ 交互层   src/ui/Hotspots.tsx          热点层（位置由适配器提供）
│           src/ui/ModulePanel.tsx       全屏内容面板
│           src/ui/Overview.tsx          总览文案与提示
├─ 适配层   src/stage/types.ts           StageAdapter 接口（渲染器无关）
│           src/stage/scene3d.ts         3D 实现（当前）
│           （将来）src/stage/flat2d.ts  2D 实现，接口不变
└─ 渲染层   src/scene/Scene.tsx          相机 / 角色 / 景深（只改输入那一段）
```

**分层的意义**：以后无论换 2D 插画还是重做 3D 模型，只需换适配层实现，数据层、状态层、交互层、面板内容**一行都不用改**。

### StageAdapter 接口（渲染器无关的契约）

```ts
// src/stage/types.ts
import type { ModuleId } from '../data/modules'

/** 热点在屏幕上的位置与可见性，由渲染器每帧提供 */
export interface HotspotFrame {
  id: ModuleId
  /** 相对视口的百分比坐标，0-100 */
  x: number
  y: number
  /** 0-1，用于随相机远近缩放热点（2D 实现可恒为 1） */
  scale: number
  visible: boolean
}

export interface StageAdapter {
  /** 把视图切到某模块；传 null 表示回总览 */
  setView(moduleId: ModuleId | null): void
  /** 订阅每帧的热点位置（返回取消订阅函数）。2D 实现可只在尺寸变化时回调 */
  onHotspots(cb: (frames: HotspotFrame[]) => void): () => void
}
```

- **3D 实现**：每帧把 `focus-*` 空对象或模型上挂点投影到屏幕坐标，写进 ref 后直接改 DOM transform（**不走 React state，避免每帧重渲染**）。
- **2D 实现（将来）**：热点位置是固定的百分比，`onHotspots` 只在 resize 时回调一次，`setView` 对应 CSS 缩放/平移。

## 5. 关键实现细节

### 5.1 Scene.tsx 的输入替换（核心改动）

```ts
// 原来（第 331-366 行）：测量 DOM 锚点 + 滚动位置 → sTarget
// 现在：
const targetIndex = (() => {
  const id = useStore.getState().active
  return id ? MODULE_INDEX[id] : -1   // -1 = 总览（帧 0）
})()
let sTarget = targetIndex
```

- `MODULE_INDEX` 由 `modules.ts` 的数组顺序推导（模块 1 → 0，模块 2 → 1 …），
  代入 `frameTarget = (sTarget + 1) * FRAMES_PER_NODE` 后得到帧 50 / 100 / 150 / 200。
- **在 `useFrame` 内用 `useStore.getState()` 直读**，不订阅 —— 避免每次切模块触发整棵树重渲染。
- `frameSmooth` 的缓动保留，`cam.damping` 可略调大以获得更明确的「飞过去」手感。
- `cam.dwell` 置 0：它原本是「滚动到节点附近时停住」的重映射，离散跳转不需要。

### 5.2 热点贴合（最容易出问题的地方）

总览态相机有**指针视差**，而热点是 DOM 层 —— 相机一动，热点就会和身体脱开。三种做法：

| 做法 | 说明 | 取舍 |
|---|---|---|
| A. 总览关掉视差 | 热点用固定百分比，绝对不会错位 | 最稳，但丢掉一点灵动 |
| **B. 同步视差位移（本轮采用）** | 3D 层每帧把当前视差偏移写进 ref，热点层读同一个值做 `translate` | 既保留视差又不错位，代价是多一个共享 ref |
| C. 真 3D 投影 | 把 glb 里挂点投影到屏幕坐标 | 最准，但要改 glb（本轮不做） |

本轮取 B；将来做 C 时只需换适配层实现。

### 5.3 面板打开时的渲染开销

面板是全屏不透明层，此时 3D 完全被遮住但仍在渲染，白烧 GPU（移动端尤其明显）。

- 面板打开时把 `<Canvas>` 的 `frameloop` 切到 `'demand'`，并停止 `useFrame` 里的相机缓动（相机已到位，无需继续）。
- 关闭时恢复 `'always'` 并重新缓动回总览。
- 这是**性能必需项**，不是优化项。

### 5.4 交互与可访问性

- **Esc / 点击面板外 / 关闭按钮** → 统一收敛到 `setActive(null)`。
- 面板打开时锁 `body` 滚动；关闭时恢复（记录原 `overflow` 值）。
- 焦点管理：面板打开时把焦点移到面板容器，关闭后还给触发的热点。
- 热点用 `<button>`，带 `aria-label`；命中区最小 44×44px（移动端）。
- 尊重 `prefers-reduced-motion`：该偏好下缩短或取消相机飞行，直接切帧。

### 5.5 降级（无 WebGL2）

热点层与面板层都是 DOM，**天然可用**；只有「相机飞过去」没有意义。

- 降级时 `Hotspots` 从「按百分比贴在形象上」退化为「整齐排列的四个入口按钮」。
- 点击直接出面板，不涉及任何 3D 逻辑。
- 复用现有的 `.scene-bg--fallback` 背景，视觉不突兀。

## 6. 分阶段实施

### Stage A —— 骨架跑通（本轮）

**范围**：数据层 + 状态层 + 适配层接口 + 热点层 + 面板骨架 + Scene 输入替换。面板内容先用**占位结构**（标题 + 说明 + 一两行真实数据）。

**验收标准**
1. 总览显示 4 个热点，位置贴在形象上，hover 有放大与标签
2. 点击任一热点 → 相机平滑飞到对应锚点，全屏面板出现
3. Esc / 点击面板外 / 关闭按钮 → 面板退场，相机飞回总览
4. 模块之间**直接互切**（不经过总览）也正常，不会出现相机乱飞
5. 快速连点不产生错位或卡死
6. 无 WebGL2 降级态下热点与面板同样可用
7. `npm run typecheck` 与 `npm run lint` 通过，`npm run build` 通过
8. 移动端 390×844 可点、可关、不溢出

**不做**：四个模块的最终视觉、热点实物造型打磨、进出场动效细化。

### 9.1 与计划的差异

### 9.3 环境限制（影响后续工作方式）

**D 盘 git 无法创建带斜杠的分支名。** `git checkout -b feat/xxx` 会打印 "Switched to a new branch"，但 `.git/refs/heads/feat/` 与 ref 文件都不创建，HEAD 指向不存在的 ref → unborn 分支（`git log` 报 "does not have any commits yet"）。

定位结论：**只出现在 D 盘**，且**只影响 git 对 `.git/refs/` 子树的目录创建**（`.git/objects/`、`.git/logs/` 均正常）；同一 git 在 C 盘完全正常。关键证据是 `git update-ref refs/heads/p4/y` 唯一产生的文件是 `.git/logs/refs/heads/p4/y` —— reflog 写进去了（三级目录创建成功），ref 文件却没有。

- **对策**：分支名一律用连字符（`feat-interactive-modules`），**禁用斜杠**。这与上一次 `.git` 被清空是同一征兆，务必规避。
- **建议**：把项目移到 C 盘可根治。

**`npm run build` 在沙箱内跑不通。** Vite 构建前清空 `dist` 时被沙箱的批量删除守卫拦截（`SAFE_DELETE_BULK_REJECTED`），**非代码问题**，需在沙箱外或新回合执行。

## 10. 视觉整改记录（Stage A+）

Stage A 交付后老大的反馈是「大致是这么个意思，但现在效果上基本上就能打个 10 分，满分一百」，
并在四类扣分原因里**全选**：面板内容太素、缺动效和空间感、面板挡住相机飞行、热点没有实物感。
本章记录这一轮的整改。

### 10.1 最重要的发现：glb 的运镜是「脸部贴纸巡游」

整改前先做了一件之前没做的事 —— **把 me.glb 的节点树直接解出来看锚点坐标**：

```
focus-0  T=[-0.0018, 0.4945, 0.2929]
focus-1  T=[ 0.2119, 0.3931, 0.2424]
focus-2  T=[ 0.2143, 0.2642, 0.2095]
focus-3  T=[-0.1915, 0.4025, 0.2698]
focus-4  T=[-0.1680, 0.3100, 0.2705]
focus-5  T=[-0.0039, 0.4340, 0.3432]
focus-works T=[-0.0105, 0.3724, 0.3953]
```

**所有锚点都落在 x ±0.21 / y 0.26–0.49 的头部范围内**，而 `Camera` 静态位置在 z = 4.13。
实拍截图证实：第 0 帧是脸部微距，`focus-1`、`focus-3` 是贴在眼睛和脸颊上的超近景
（模型脸上贴满了 STICKER：I❤SYSU、HOTSAR、抖音、熊头……）。

**结论：身体上的东西 —— 工牌、背包、名片 —— 在任何一帧都不在画面里。**
这是「热点没有实物感」的真正根因：不是图标画得不好，是**四个热点无论放哪都在脸上**。
Stage A 的「实拍校准」之所以看着对，是因为当时是在错误的画面上量的坐标。

### 10.2 对策：总览态拉远（`cam.overviewPullback`）

不改 glb（需要 Blender），改为在渲染层叠一个**总览态拉远**：

```ts
// Scene.tsx
overviewPullback: 2.0,   // 总览态沿「焦点→相机」方向整体拉远

// useFrame 内，与帧缓动共用同一个 a，切换模块时不跳变
const pullTarget = sTarget === OVERVIEW_INDEX ? cam.overviewPullback : 1
pullSmooth.current += (pullTarget - pullSmooth.current) * a
...
tmpVec.current.multiplyScalar(pullSmooth.current)
if (isMobile.current) tmpVec.current.multiplyScalar(cam.mobilePullback)
```

效果：总览态人物占画面高约 55%，头、肩、胸都进画面 → **热点终于有处可贴**；
进入任一模块时拉远量平滑归零，构图交回 glb 的运镜。

> ⚠️ **这条是热点坐标的校准前提**。改 `overviewPullback` 后必须重新校准
> `data/modules.ts` 的 hotspot 坐标（该文件顶部已写明）。

### 10.3 热点实物化

- 新增 `ui/HotspotIcons.tsx`：工牌 / 眼镜 / 背包 / 名片四个线描图标（24×24、strokeWidth 1.8）

### 11.4 背景「空」的根因与对策

**根因不是「缺东西」，而是「没有深度线索」。**

`GradientBackground` 是一个 scale=100 的球，用 shader 做上下渐变，全程静止、纯二维；
`NoiseOverlay` 是全局胶片噪点，不提供空间信息。二者叠在一起就是一张「纸」。
10.2 引入 `overviewPullback = 2.0` 之后人物缩小、留白变大，这个问题被放大了。

对策是在人物背后撒一批微小颗粒（`src/scene/Ambient.tsx`），
靠现有的 `DepthOfField` 把它们虚化成柔光斑 —— 后处理是现成的，不用另写 shader。
再按深度做**半径补偿**（越远越大，抵消透视缩小）与**颜色衰减**（越远越暗，
additive 混合下即越淡），画面就有了「人物 → 近处颗粒 → 远处光晕 → 渐变」四层。

颗粒只在总览态显示，打开面板时随 `active` 淡出 —— 面板态相机会飞到脸上，
颗粒糊在画面里只会干扰阅读。

**三个调参时踩到的坑**（都写在 `Ambient.tsx` 文件头）：

| # | 坑 | 现象 | 修正 |
|---|---|---|---|
| 1 | 颗粒设 `depthWrite={false}` | 深度图里它们在「最远」，DoF 无法区分远近，纵深全丢 | 改为 `depthWrite` |
| 2 | 用固定世界范围撒点（x ±13 / y -3~11.5） | 九成颗粒落在画面外 | 按每个 z 平面反推可见范围后再采样 |
| 3 | 半径给到 0.27 | 画面像下雪 | 压到 0.02~0.12；`bokehScale` 7.4 且 `focusRange` 只有 2 单位，颗粒 CoC 会饱和到 1，统一糊成约 14px 半径的光团 |

> 关键数字：**总览态相机离焦点只有约 5 世界单位**（由截图反推：人物头部到胸口
> 约占画面高 55%，对应可见高度约 2 单位）。这比按 glb 静态相机位置估算的 17 单位
> 小得多 —— 坑 2 就是这么来的。改 `overviewPullback` 后 `Ambient.tsx` 的
> `CAM_DIST` 要跟着改。

另有两条分布约束：中间竖带（`TEXT_ZONE_X`）抬高避开底部文案区；
漂浮幅度压到 0.26 世界单位以内（`amp`），否则颗粒会漂到文字上，把避让白做。

> **结局：这层已被移除**（同日，见 11.8）。`Ambient.tsx` 删掉了 —— 保留以上记录是因为
> 三个坑的结论对以后任何「往背景里加东西」的尝试都成立，尤其是「总览态相机离焦点
> 只有约 5 单位」和「景深对远景物体是饱和虚化」这两条。

### 11.5 工具：Windows 下无头截图的视口坑

`chrome --headless --screenshot --window-size=390,844` 在本机**拿不到 390 宽的视口**：
Windows 下 Chrome 有约 512×512 的最小窗口限制，传 390 会被静默抬到 512，
结果是「按 512 宽布局、只截 390 宽」—— 右侧内容被切掉，看着像页面横向溢出。

`--headless=old` 与 `--force-device-scale-factor` 都绕不过去（实测视口仍是 512×746 / 758×1590）。
最终方案是 `scripts/cdp-shot.mjs`：用 CDP 的 `Emulation.setDeviceMetricsOverride`
直接覆盖布局视口，与窗口尺寸无关。脚本同时处理了触摸模拟
（`setTouchEmulationEnabled`）—— 不开的话 `matchMedia('(pointer: coarse)')` 为 false，
`Scene.tsx` 会走桌面分支，截出来的不是真机布局。

逐帧检查没有跳变（`scripts/glb-camera-trace.py`）。所以**不是烘焙动画本身的问题**。

`Scene.tsx` 的过渡也只有一行：`frameSmooth += (frameTarget - frameSmooth) * a`，
`a = 1 - damping^dt`（`damping = 0.1` → 每帧走 3.76%，时间常数 0.43s）。
数学上连续，看着也不该是硬切。

### 13.2 真正的原因：三件事叠在一起

把 glb 曲线喂进 `Scene.tsx` 的公式逐帧算一遍（`scripts/glb-transition-sim.py`），三件事一起暴露：

**① 第 0 帧和第 200 帧之间不是「一段路」，是「绕脸巡游」**

| | 净位移 | 净转角 | 路径累计转角 |
|---|---|---|---|
| 第 0 帧 → 第 200 帧 | 7.60 世界单位 | 54.5° | **213°** |

相机沿路来回摆，净转角只有 55° 却累计转了 213°。让它沿帧轴滑过去，
等于把这段 8 秒的巡游按 5 倍速播一遍。

**② 人物自己还在高速自转**

`manAction` 在第 0→97 帧让 `man` 节点转了 **330°（整整一圈）**，之后才停在 +30.9°。
镜头绕、人也在转，两个旋转叠加。

**③ 一阶缓动起步速度最大，把最猛的一段全挤在头 100ms**

`frame += Δ·a` 在 t=0 时速度最大。200 帧的跨度下：

| 时间 | 已走帧数 | 该段含多少位移 |
|---|---|---|
| 0–100ms | 0 → 41 | **62%** |
| 100–350ms | 41 → 110 | 缓慢爬行 |
| 350–450ms | 110 → 127 | 第二段鞭打，峰值 20.9°/步 |

合起来就是：一冲 → 一顿 → 再一冲 → 停。峰值 **16.3°/步 + 20.9°/步**，
相机中途还穿过焦点（最近 0.96 世界单位，几乎贴到脸上）。这就是「两个机位硬切」的来源。

### 13.3 修复：预烘机位表 + 机位间直接插值

核心改动：**不再让相机沿帧轴滑过中间所有机位，而是在「出发机位」和「目标机位」之间直接插值。**

1. **预烘机位表**（`useEffect` 里一次性做）
   逐整数帧（0…250）跑 `mixer.update(0)` + `decompose`，把相机姿态与 `man` 朝向
   存进 `shots.current`。运行时读不到 R3F 的相机对象，这是唯一能拿到世界变换的时机。

2. **过渡 = 两台机位之间插值**
   ```
   camera.position   = focus + (lerp(posFrom, posTo, k) - focus) × pull
   camera.quaternion = slerp(quatFrom, quatTo, k)
   man.quaternion    = slerp(bodyFrom, bodyTo, k)      // 必须在 mixer.update(0) 之后覆盖
   ```
   人物朝向也走直线插值，否则镜头直线飞、人在原地转一圈，还能看到后脑勺。

3. **时长按行程定**，不写死
   `clamp(0.55 + (位移 + 转角°×0.06) × 0.075, 0.7, 1.9)` 秒。
   定长会让相邻机位之间慢吞吞、跨全场的又太急；按行程给时长，观感速度才一致。
   实测取值：总览→个人信息 1.32s、→联系方式 1.37s、个人信息→联系方式 1.16s。

4. **进度曲线 `easeShot`：五次平滑 + t^0.7 前倾**
   纯 smootherstep 起步太黏（前 300ms 只走 5%），而面板入场延迟是 0.14s/0.3s，
   结果面板先盖上来、镜头在背后飞完。前倾后 300ms 走 23%、600ms 走 61%，
   峰值速度只从 1.875×平均 变到 1.81×平均（几乎没变，只是峰值位置从 t=0.5 前移到 t=0.3）。

5. **单帧步长封顶 50ms**
   切模块时会挂面板（React 渲染 + 二维码解码），实测能卡到 110ms。
   不封顶的话那一帧一口气推进 8% 进度，缓动再平滑也救不了。

6. **中途换目标以「当前实际位置」接力**
   出发端每次取 `baseCur/quatCur/bodyCur`，所以飞行途中再点别的模块是连续变向，不跳。
   实测切换瞬间位移 0.000、转角 0.00°。

### 13.5 新增诊断工具

相机状态在运行时一直读不到（R3F 没把 store 挂到 canvas 上，只有 `__reactFiber`），
无头 Chrome 的 `Page.startScreencast` 又抓不到 WebGL 图层（实测 82 帧全黑）。
这次把口子补上了：

- **`Scene.tsx` 在 DEV 下挂 `window.__scene`**：每帧写相机位置/朝向/帧号/进度。
  生产构建里 `import.meta.env.DEV` 是静态 false，整段会被摇掉。
- **`scripts/cdp-camera-trace.mjs`**：用 rAF 采样 `window.__scene`，逐帧算位移/转角，出峰值。
- **`scripts/glb-transition-sim.py`**：把 glb 曲线按 `Scene.tsx` 的公式离线算一遍。
  两种模式 —— `frame`（旧的帧轴滑行）/ `shot`（新的机位插值），`pairs` 打印机位间行程表。
  **不用开浏览器就能调过渡参数**，这次曲线和时长都是在这上面定下来的。
- **`scripts/cdp-transition.mjs` + `scripts/strip.py`**：连拍截图拼故事板。
  配 `?nopanel=1` 用，能把镜头飞行完整露出来。

踩过的坑（都写进脚本头注释了）：
- glb 关键帧时间从 **1/24 开始不是 0**；`scale` 通道只有 2 个关键帧而 translation/rotation
  有 350 个 —— **每个通道必须各用各的 times**，共用一个会静默串位，表现为「相机完全不动」。
- 沙箱里 `http_proxy` 指向本机代理，Chrome 走系统代理会把 localhost 也代理出去（502/空页面），
  启动参数加 `--no-proxy-server`。
